# Milestone models

- `config/milestone_models.yaml` is the public catalog; releases are chronological, source-backed official milestones, with variants grouped under generations. Model-family navigation sorts names case-insensitively across topics.
- `catalog.py` validates metadata; `publisher.py` renders family and reading pages; `reader.py` owns loopback-only deep reading. Reuse local Markdown notes and preserve existing notes and generated readings when adding families.
- Date-based note IDs may collide across model releases. Resolve explicit `milestone_family` and `milestone_release` before legacy ID-only notes; never treat a note explicitly assigned to another release as a fallback.
- GPT, Claude and DeepSeek track general-purpose language/reasoning releases; QwenVL tracks the named Qwen-VL lineage. Do not silently add unrelated product or specialized model families. Undisclosed technical information stays `/`; missing reading stays visibly pending.
- Monthly maintenance verifies official release announcements and dates before appending milestones, rebuilds affected pages and search, and records private evidence under ignored `build/reports/`. Tests and temporary scripts are local only and deleted after verification. Do not edit README.

## Monthly model-maintenance receipts

- Run commands from the repository root in the existing WSL project virtual environment, with the project installed into that environment. If the package is not installed, prefix every command with `PYTHONPATH=src`, for example `PYTHONPATH=src python -m milestones.maintenance status`.
- Run `python -m milestones.maintenance status` at the start of the monthly model job. Its JSON `due_families` array is the complete retry queue; check every listed family independently.
- The maintenance CLI records evidence but does not discover releases. For each due family, inspect current official announcement or release pages, verify release names and dates, and update the public catalog through the existing catalog workflow when needed.
- After a completed check, record exactly one result with `python -m milestones.maintenance record <family> --status unchanged|updated --observed-at YYYY-MM-DD --summary "..." --evidence-url https://...`. A successful check requires at least one official HTTPS evidence URL. `updated` means the verified catalog change has already been applied; `unchanged` means the official sources were actually inspected and no catalog change was needed.
- A URL by itself is not verification. `observed_at` is the date the source was inspected, and `summary` states what was observed. Do not reuse a prior summary or infer verification from a reachable URL.
- If discovery, source access, verification, or catalog update cannot be completed, record `--status failed` with the observed date and a concrete failure summary. Evidence URLs are optional for failures. A failure preserves the previous successful check and remains due on the next run.
- `observed_at` is the source-inspection date expressed as a UTC calendar date; convert from local time before recording it. It cannot be later than the current UTC date. An older successful observation is recorded for audit but remains due when it belongs to a previous UTC calendar month.
- For structured automation input, pass `--receipt <json-path>` instead of inline evidence fields. The JSON object contains only `family`, `status`, `observed_at`, `summary`, and `evidence_urls`. Store temporary input and the generated per-family receipts only below ignored `build/reports/model-maintenance/`.
- Global overrides precede the subcommand: `python -m milestones.maintenance --catalog <yaml> --receipts-dir <dir> status`. The default catalog is `config/milestone_models.yaml`; CLI receipt paths are restricted to `build/reports/model-maintenance/` or its descendants after symlink resolution. Direct Python function calls may inject temporary receipt directories for local tests.
